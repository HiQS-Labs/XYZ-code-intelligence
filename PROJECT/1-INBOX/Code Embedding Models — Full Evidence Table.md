# Code Embedding Models for Local Code RAG on Apple Silicon — Source-Cited Evidence Table

**Scope of the question:** is it worth fine-tuning `BAAI/bge-small-en-v1.5` locally (Apple Silicon) for retrieval over private repos containing Python, JS/TS, PHP, HTML/server-rendered templates, plus Markdown/tests/config/routes/API schemas — or is a different compact checkpoint a better starting point?

Parameter counts marked "(safetensors)" come from Hugging Face's own repo metadata API, which reports the tensor count in the repo. ## 1. Executive summary — the BGE-small-for-code question

**There is no credibly evaluated code-search fine-tune of `BAAI/bge-small-en-v1.5`.** BAAI itself never shipped a small BGE code model: its only code embedding release is `BAAI/bge-code-v1`, which is not a BGE-small derivative at all — it is a 1.54B-parameter `Qwen2Model` (Qwen2.5-Coder class) with 1536-dim output and 32k context ([config.json](https://huggingface.co/BAAI/bge-code-v1/resolve/main/config.json), [repo metadata](https://huggingface.co/api/models/BAAI/bge-code-v1)). Querying the Hugging Face model index for every checkpoint declaring `base_model:finetune:BAAI/bge-small-en-v1.5` returns 383 models, of which exactly two are code-related: `Matthieufromparis/bge-small-code-search-v1` and `ArnavKewalram/bge-small-code-v1` ([HF models API, filtered](https://huggingface.co/api/models?filter=base_model:finetune:BAAI/bge-small-en-v1.5&limit=1000)). Both are weak evidence. The first was trained on only 6,000 CodeSearchNet Python pairs and reports NDCG@10 improving from 0.9761 (base) to 0.9849 on 500 held-out CodeSearchNet Python pairs — a saturated, single-language, self-built eval whose base-model score of 0.976 is itself implausibly high for real code search, indicating an easy candidate pool rather than a benchmark ([model card](https://huggingface.co/Matthieufromparis/bge-small-code-search-v1)). The second has **no license declared at all** and its card reports an "Unnamed Dataset" of 200,000 anchor/positive/negative triples with an `InformationRetrievalEvaluator` on a `cornstack_eval` split, but **publishes no evaluation numbers** ([model card](https://huggingface.co/ArnavKewalram/bge-small-code-v1), [repo metadata](https://huggingface.co/api/models/ArnavKewalram/bge-small-code-v1)). A BGE-large LoRA variant (`jamie8johnson/bge-large-v1.5-code-search`) is the only BGE-derived code fine-tune that reports a recognized benchmark — CoIR 9-task overall 57.5 vs. 55.7 for the BGE-large baseline, and CodeSearchNet (6 languages) NDCG@10 0.779 vs. 0.721 ([model card](https://huggingface.co/jamie8johnson/bge-large-v1.5-code-search)) — but it is a single-author repo with self-run evals and no paper.

**Why BGE-small is a poor base regardless of the fine-tune:** `bge-small-en-v1.5` is a 33.4M-parameter BERT with 384 dims, a **512-token limit**, English-only training on unnamed "large-scale pairs data," and no code benchmark of any kind reported on its card ([model card](https://huggingface.co/BAAI/bge-small-en-v1.5), [config.json](https://huggingface.co/BAAI/bge-small-en-v1.5/resolve/main/config.json)). Its tokenizer is the 30,522-token `bert-base-uncased` vocabulary, which is uncased and not code-aware — a structural handicap for exact symbol lookup (`getUserById`, `$wpdb`, `__init__`) that fine-tuning on your own data cannot undo.

**Better starting points exist at the same or smaller size.** The strongest finding of this research is `Shuu12121/NightOwl-CodeEmbedding-35M`: 34,094,976 params, 384 dims, 1,024-token context, ModernBERT with a **50,368-token custom code BPE**, trained with 15 mined hard negatives per anchor and reporting a full MTEB(Code, v1) sweep — macro average 0.65555 across 12 tasks, CodeSearchNetRetrieval 0.86228 with per-language breakdown (Python 0.8926, JS 0.7718, PHP 0.8676), and explicit decontamination against the CodeSearchNet test split ([model card](https://huggingface.co/Shuu12121/NightOwl-CodeEmbedding-35M), [repo metadata](https://huggingface.co/api/models/Shuu12121/NightOwl-CodeEmbedding-35M)). That is the same footprint class as BGE-small with real code-retrieval evidence attached. Its 150.8M sibling scores 0.70907 macro ([model card](https://huggingface.co/Shuu12121/NightOwl-CodeEmbedding)), and `nomic-ai/CodeRankEmbed` (136.7M, MIT, 8,192 context) reports CSN MRR 77.9 / CoIR NDCG@10 60.1 with ONNX ports available ([model card](https://huggingface.co/nomic-ai/CodeRankEmbed), [repo metadata](https://huggingface.co/api/models/nomic-ai/CodeRankEmbed)).

**Two corpus-specific warnings.** (a) **HTML/templates are a near-universal gap.** Of every model examined, only `jinaai/jina-embeddings-v2-base-code` explicitly lists HTML, CSS, Markdown, Dockerfile, Makefile and Shell among its 30 supported languages ([model card](https://huggingface.co/jinaai/jina-embeddings-v2-base-code)); the code-specialist retrievers are trained on function/docstring pairs in 6–9 languages (CodeSearchNet's Go/Java/JS/PHP/Python/Ruby, sometimes + Rust/TS) and say nothing about templates, routes, or config/schema files. Blade/Twig/Jinja templates and OpenAPI YAML are out-of-distribution for essentially all of them. (b) **Benchmark leakage is systemic in this space.** NightOwl trains directly on the CoIR/MTEB-Code training splits and states its scores are "in-domain … not strictly zero-shot" (its card reports a **zero-shot fraction of 8%**) ([model card](https://huggingface.co/Shuu12121/NightOwl-CodeEmbedding-35M)); jina-code-embeddings likewise trains on MTEB code task training splits ([paper](https://arxiv.org/html/2508.21290v1)); CodeBERT, GraphCodeBERT, CodeT5 and the CodeSearchNet fine-tunes all train on CodeSearchNet, the same corpus their scores are reported on. Treat all CSN/CoIR numbers as upper bounds and validate on your own repo.

## 3. Strongest candidates

1. **`Shuu12121/NightOwl-CodeEmbedding-35M`** — [card](https://huggingface.co/Shuu12121/NightOwl-CodeEmbedding-35M). The direct drop-in replacement for BGE-small: identical footprint class (34.1M params, 384 dims, 130 MiB FP32) and identical sentence-transformers ergonomics, but with a code-native 50,368-token BPE, 1,024-token context (2× BGE-small), 15 mined hard negatives per anchor, explicit CSN-test decontamination, and a complete MTEB(Code, v1) sweep at macro 0.65555 with per-language CSN numbers covering Python (0.8926), PHP (0.8676) and JS (0.7718). It even publishes its own weakness (8% zero-shot, in-domain caveat), which is the strongest signal of honest evaluation in this entire set. Best first move: benchmark it head-to-head against your current BGE-small index before spending any GPU time on fine-tuning.
2. **`nomic-ai/CodeRankEmbed`** — [card](https://huggingface.co/nomic-ai/CodeRankEmbed). 136.7M params, MIT, **8,192-token context**, CSN MRR 77.9 / CoIR 60.1, and community ONNX/int8 ports for CPU-cheap local serving. The 8k window is the key differentiator for "how does this work?" queries that need whole files or multi-function context, which every 512/1,024-token model truncates.
3. **`Shuu12121/NightOwl-CodeEmbedding` (150.8M)** — [card](https://huggingface.co/Shuu12121/NightOwl-CodeEmbedding). If you can afford 575 MiB and 768-dim vectors, it buys +5.4 macro points over the 35M (0.70907 vs 0.65555) with the same hard-negative recipe and decontamination, and was updated 2026-08-23 — the most recent code retriever found.
4. **`codesage/codesage-small-v2`** — [card](https://huggingface.co/codesage/codesage-small-v2). 130M, Apache-2.0, StarCoder tokenizer, and the only compact model publishing **per-language NL2Code numbers that include PHP (60.20), JS (65.77) and TypeScript** alongside Python (68.79), plus MRL for cheap index truncation. Provenance is unusually explicit (The Stack → The Stack V2 with consistency filtering).
5. **`jinaai/jina-embeddings-v2-base-code`** — [card](https://huggingface.co/jinaai/jina-embeddings-v2-base-code). Apache-2.0, 161M, 8,192 context, and the **only** model whose declared language list explicitly includes HTML, CSS, Markdown, Shell, Dockerfile and SQL — directly addressing the template/config/schema part of your corpus that every other candidate ignores. Accept that its retrieval quality is mid-pack (third-party CoIR 58.4, CSN-PHP 0.5701) and that it publishes no eval itself.
6. **`jinaai/jina-code-embeddings-0.5b`** — [card](https://huggingface.co/jinaai/jina-code-embeddings-0.5b), [MLX port](https://huggingface.co/jinaai/jina-code-embeddings-0.5b-mlx). The best sub-1B code retriever measured anywhere in this set (MTEB-Code 78.72%, CoIR 73.94, Code2Code 90.37%, 32k context) *and* the only one with an official Apple-Silicon MLX build with Metal acceleration. **Use only if non-commercial CC-BY-NC-4.0 is acceptable** for your setting; if the repos are commercial property, this is disqualified and `Qwen/Qwen3-Embedding-0.6B` (Apache-2.0, mature MLX ecosystem, third-party MTEB-Code 74.69%) is the closest licensable substitute.

**Bottom line on the original plan:** fine-tuning `bge-small-en-v1.5` starts from an English-text encoder with an uncased non-code tokenizer, a 512-token window, and no code evaluation whatsoever, and the only two existing code fine-tunes of it are a 6k-pair Python toy and an unlicensed checkpoint with no published numbers. The same local footprint is available from checkpoints already trained on code with hard negatives and published per-language retrieval scores. Fine-tune *on top of one of those* (NightOwl-35M or CodeRankEmbed) rather than on top of BGE-small, and add a separate strategy — jina-v2-base-code, or lexical/BM25 hybrid — for HTML/templates/config/schema files, which no code embedding model in this survey claims to cover.

## 4. Method and evidence notes

- Fine-tune discovery used the Hugging Face models API with the `base_model:finetune:` filter, which enumerates declared derivatives: 383 for [`BAAI/bge-small-en-v1.5`](https://huggingface.co/api/models?filter=base_model:finetune:BAAI/bge-small-en-v1.5&limit=1000) and 9 for `BAAI/bge-small-en`, plus keyword sweeps of the model index for `bge code`, `code-search`, `code-embedding` ([example](https://huggingface.co/api/models?search=code-embedding&limit=60&sort=downloads)).
- Parameter counts labeled "(safetensors)" and all "last update" dates come from each repo's `https://huggingface.co/api/models/<id>` record (`safetensors.total`, `lastModified`), fetched this session. Architecture, hidden size, layer count and max position embeddings come from each repo's `config.json`.
- No HF Space, dataset viewer, discussion thread or commit was used as evidence that a trained model exists. Where a repo's file list mattered (LoRA-only vs merged weights), it was read from the API `siblings` list.
- Raw README files were read via `https://huggingface.co/<id>/raw/main/README.md` for the benchmark tables that the rendered pages truncated (CodeSage NL2Code, CodeT5+ CodeXGLUE, OASIS CoSQA/AdvTest/CSN).
- Footprint numbers marked "est." are arithmetic (params × bytes/param) over the verified counts above, not statements found on any page. NightOwl is the exception: 130 MiB / 575 MiB are stated on its cards.
